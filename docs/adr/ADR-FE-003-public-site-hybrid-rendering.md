# ADR-FE-003 — Hybrid Rendering for the Public Application

**Status:** Accepted

## Context

The public application contains durable reference content such as game rules,
classes and monsters, as well as pages whose content may require server-side
evaluation. The course explicitly requires the cohort to implement and justify
SSR.

Rendering every page in the same way would either make static content needlessly
expensive to serve or prevent the project from using SSR where it answers a real
need.

## Decision

The public Nuxt application SHALL use hybrid rendering:

- stable public reference pages SHALL be statically generated by default;
- routes requiring request-time data, personalisation or another demonstrated
  server-side concern SHALL use SSR;
- the rendering mode of every non-default route SHALL be documented with its
  reason and validation evidence.

The public application SHALL NOT use CSR as its default rendering mode.

## Consequences

- Static content is inexpensive to serve and resilient to backend unavailability.
- The project demonstrates SSR only where it has a concrete purpose.
- Route ownership includes declaring and maintaining the rendering mode.
- SSR routes require server runtime capacity and an explicit caching strategy.

## Alternatives Considered

- CSR for all public pages: rejected because it does not address the SSR
  requirement and delays useful content until JavaScript has loaded.
- SSR for every public page: rejected because stable content does not need a
  request-time render.
- Static generation for every public page: rejected because it would preclude
  justified SSR use cases.
